# 铁路桩号换版核查

铁路台账只存桩号。换版前，用这个网页工具核查：哪些旧号能自动迁移、对应哪个新号；
哪些必须先补段号或人工处理。

## 规则

桩号表每行一段，四列：

| 段号 | 里程起点 | 里程终点 | 起点桩号 |
|------|----------|----------|----------|
| K1   | 0        | 500      | 1000     |
| K2   | 500      | 900      | 1500     |

* 里程与桩号均为**整数米**；
* 里程区间**左闭右开**：`[里程起点, 里程终点)`；
* 段内每增加 1 米，桩号加 1：桩号区间为 `[起点桩号, 起点桩号 + 里程长度)`。

一个旧号 `x` 只有在以下四条全部成立时才判为**可迁移**：

1. 旧表中恰好一个段覆盖 `x`（旧号在全线唯一）；
2. 该工程里程在旧表中恰好对应一个段（否则一个位置对应多个旧号，无法判断迁移谁）；
3. 新表中恰好一个段覆盖该工程里程（该工程位置有新号）；
4. 换算出的新号在新表中恰好出现一次（新号在全线唯一）。

其余旧号按区间分类，并列出相关段号：

| 状态 | 含义 |
|------|------|
| 可迁移 | 四条件全满足，给出旧号区间与对应新号区间 |
| 缺号 | 旧表没有任何段覆盖该桩号，先补段号/补录 |
| 重号（旧表） | 旧表桩号区间重叠，或同一工程里程对应多个旧号 |
| 新表未覆盖 | 新表没有覆盖该工程里程，先在新表补段 |
| 重号（新表） | 同一工程里程在新表被多段覆盖，或算出的新号在新表重复 |

“相关段号”一列：可迁移区间显示“旧段号 → 新段号”，异常区间显示涉及的段号
（缺号显示前后相邻旧段，新表未覆盖显示前后相邻新段）。

> 注：桩号本身不是连续编号的“公里标 K1+234”文本，工具按**整数米**数值处理，
> 例如 `起点桩号 1000` 表示 1000 m。

### 长区间不逐米展开

算法收集旧号空间中分类可能变化的边界（旧段桩号端点、新旧段里程交叠端点、
新号重叠区映射回旧号的端点），把查询区间切成若干段，每段取一个样本点判定，
再合并相邻同状态区间。复杂度只与**段数和边界数**有关，与区间长度无关：
1 亿米长的区间也只有几个区间输出，耗时毫秒级。

## 运行（Docker Compose）

```bash
docker compose up --build
```

打开 <http://localhost:8000>。页面内提供两份示例表下载：

* `samples/old_v1.csv` / `samples/new_v1.csv`（旧号 1000–2499）
* 示例故意包含：可迁移、缺号、旧表重号、新表未覆盖、新表重号五类情况。

演示步骤：

1. 在首页上传两份示例表，范围填 `1000`–`2499`，点“开始核查”；
2. 结果页顶部“换旧号范围复查”里把范围改成 `1500`–`1849` 再提交，
   页面与下载随即切到新范围，无需重新上传；
3. 回填 `1000`–`2499` 再次复查，可验证两版表与索引始终复用、结果不变；
4. 每个结果页的“下载可迁移区间 CSV”只导出该次范围的可迁移区间。

停止：`docker compose down`。

## 输入格式

* 支持 CSV（UTF-8 / UTF-8 BOM / GB18030，逗号、分号或制表符分隔）和 XLSX（首个工作表）；
* 表头支持中文（段号, 里程起点, 里程终点, 起点桩号）或英文
  （segment_no, start_mileage_m, end_mileage_m, start_chainage）；
* 文件 ≤ 20 MB；单元格必须为整数，`1.5` 这类小数会被拒绝并报告行号。

## 输出与下载

* 页面按区间列出全部核查结果；
* “下载可迁移区间 CSV”**只含可迁移区间**，列为：
  `旧号起, 旧号止, 旧号个数, 新号起, 新号止, 旧段号, 新段号`；
* 每次核查（含复查）都有自己的下载链接，只指向那次的范围与结果；同一会话
  多次复查互不覆盖；
* 下载链接指向内存中的结果，有效期 1 小时或直到服务重启，需重新核查。

## 结果页换范围复查

首次核查成功后，结果页顶部多一张“换旧号范围复查”表单。工务员逐个核查工区时
可以直接改旧号起止再次提交：

* 两版桩号表、全线判重所需的索引（旧表里程重叠、新表桩号重叠）随会话保留，
  复查**不需要重新上传**；
* 切分边界按旧段惰性准备：某旧段首次被命中时才计算，换查该段另一截直接复用
  会话里的缓存；
* 并发首次命中同一旧段的请求共用一次准备（单飞），并得到同一成败结论；
* 准备失败时页面显示具体原因并保留表单，可直接再次提交；失败不写入缓存，
  下一次提交会重新尝试。只涉及已就绪段的复查不受影响，可照常完成；
* 复查仍按**全线**规则判重，页面与 CSV 与“单独上传同一份表、同一范围”完全一致；
* 会话与全部复查下载数据有效期 1 小时。会话失效后复查入口和该会话的下载链接
  一并失效，访问时提示返回首页重新上传。

## 已知限制

* 只接受整数米；不做“K1+234”文本格式解析（如需要可先转成整数米）。
* 会话与结果缓存为单进程内存，多副本部署时应改为共享缓存；当前 compose 只起
  一个实例，会话在进程重启后失效，需要重新上传。
* XLSX 只读第一个工作表。
* 不判断桩号方向（里程递增而桩号递减），只按“段内每米加一”处理；若业务上存在
  桩号随里程递减的段，需要另行约定。
* 实际耗时随**段数**增长：5000 段约 0.2 秒；接近 90 万段（约 28 MB CSV）解析约
  25 秒、核查约 40 秒。段数极多时建议先在台账中筛出目标线路/区段。

## 验证情况

* `pytest`：108 个用例全部通过，覆盖区间分类、CSV/XLSX 解析、错误输入、
  下载内容、HTTP 端到端流程，以及复查会话的边界复用、并发单飞、失败重试与
  会话回收。
* 另以逐米枚举为基准，对 9000 组随机表（含桩号重叠、里程重叠、缺段、空隙）
  做对照，结果完全一致。
* 1 亿米长的查询区间在网页流程中毫秒级返回，未逐米展开。
* 换范围复查与单独上传同一份表、同一范围逐行对照：抽查 `0-999`、`1000-1099`、
  `1850-2099`、`900-3000` 四个范围，页面结果表与 CSV 完全一致；连续复查后，
  此前各次下载链接仍返回各自范围的结果。
* 并发：20 个并发复查首次命中同一批旧段，全部 200 且页面结果一致；单元测试中
  8 线程首次命中同一旧段只准备 1 次；5 线程并发失败拿到同一原因、只准备 1 次，
  随后修正即可成功复查。
* 会话过期（TTL 或进程重启）后，复查入口与该会话的全部下载链接同时返回 404，
  页面提示重新上传；只涉及已就绪旧段的复查不受其它段准备失败影响。
* 本机无 Docker 守护进程，无法实际执行 `docker compose up --build`；本次演示
  使用同一镜像入口 `python -m uvicorn app.main:app` 直接启动，通过真实 HTTP
  完成上传、换范围复查、下载与错误流程验证。`docker-compose.yml` 未改动，依赖
  仍按 `requirements.txt` 安装。
